# Phase 13 - Perfetto Trace Usability Improvements

## Scope

```text
tools/perfetto/trampoline_to_perfetto.py
```

This is an offline visualization change. `trace.json` remains the raw
Trampoline trace and `tools/runtime_monitor/runtime_monitor.py` remains the
authoritative AUTOSAR semantic decoder.

## Purpose

The original export created all static tracks, but configured entities with no
runtime record were difficult to distinguish from missing tracks. Resource
operations were also shown as independent instants rather than ownership
durations. The update makes the configured AUTOSAR model and resource hold
periods visible in Perfetto.

## Exporter Behavior

The output metadata schema is:

```text
linux-autosar-perfetto-v3
```

The exporter creates `CONFIGURED` instant events at timestamp zero for every
non-Dummy static entity:

```text
AUTOSAR task      task, priority, activation, schedule
AUTOSAR alarm     alarm, autostart, action
AUTOSAR resource  resource, priority_ceiling
AUTOSAR event     task, event, mask
```

`DummyAlarm` and `DummyResource` intentionally do not receive a
`CONFIGURED` event. Their ID-0 reservation purpose remains visible through
their named Perfetto tracks.

Configured task lane names include the OIL/static-info priority:

```text
RTI_Task [priority=6]
TcpIp_Task [priority=8]
```

The priority values are generated by Trampoline static information and can
differ from the OIL source priorities after Trampoline priority conversion.
The idle lane has no configured priority.

## Resource Visualization

Derived `RESOURCE_ACQUIRE` records now begin a Perfetto slice:

```text
name = HELD
ph   = B
```

The matching `RESOURCE_RELEASE` emits the corresponding `ph = E`. The slice
includes AUTOSAR resource ID, resource name, and derived owner task in its
arguments. An unmatched release remains visible as:

```text
RELEASE_UNMATCHED
```

Any resource still held when capture ends is closed at the trace boundary, so
the generated JSON remains structurally valid for Perfetto.

## Configured but Inactive Entities

For the captured `trace.json`, these items have no matching runtime operation:

```text
OsResource_DdsNetio    resource ID 3: no acquire/release record
RTI_SemaphoreAlarm    alarm ID 4: no timeobj_expire record
RTI_GiveEvent         RTI_Task event mask 1: no set/reset record
RTI_TimeoutEvent      RTI_Task event mask 2: no set/reset record
```

They are still published as `CONFIGURED` in Perfetto. This denotes static
configuration, not runtime execution. The absence of `RTI_SemaphoreAlarm`
expiration does not establish whether it was armed then cancelled; raw
Trampoline tracing records expiration, not alarm set/cancel operations.

`OsResource_DdsNetio` has a configured OIL resource and task usage, but a
trace will display runtime `HELD` intervals only after the executing binary
actually calls `GetResource()` for generated resource ID 3. A mutex call alone
is not sufficient unless its OSAPI mutex implementation maps to that resource.

## Run and Validate

```bash
cd ~/autosar_virtual

./trace.sh trace.json
```

Expected integrity conditions:

```text
RAW_RECORDS == DERIVED_RECORDS
PARSER_WARNINGS=0
TRACE_INCOMPLETE=no
```

Inspect static configuration and resource intervals in the generated artifact:

```bash
jq '.traceEvents[] | select(.name == "CONFIGURED")' perfetto_trace.json
jq '.traceEvents[] | select(.name == "HELD")' perfetto_trace.json
```

Check resource acquisition at the authoritative semantic layer:

```bash
grep 'resource=OsResource_DdsNetio' runtime.txt
```

Generated artifacts remain excluded from source control:

```text
runtime.txt
perfetto_trace.json
```

## Result

```text
PASS
```

Perfetto now separates static AUTOSAR configuration visibility from observed
runtime behavior, exposes task priority in lanes and event arguments, and
represents resource ownership as time intervals.
